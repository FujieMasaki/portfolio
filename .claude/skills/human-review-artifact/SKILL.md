# /human-review-artifact

PRの作成者側が、人間のレビュアー（このプロジェクトでは主にユーザー本人）へ渡すガイドページを作る。
機械が確かめ終えたことと、人間が判断することを切り分け、判断が必要な項目だけを、PRの中の実物を
見ながら確かめられるようにする。あわせて、人間が自分でコードを読んで理解するための地図を載せ、
人間が書いた理解の答え合わせ（手順5）もこの skill で行う。

似た名前の全プロジェクト共通のコマンドとは役割が違う。

| | 誰が使うか | 何をするか |
| --- | --- | --- |
| `/review-guide` | レビュアー | 他人のPRを一問一答でレビューする |
| `/self-review` | PRの作成者 | 変更内容を理解するために解説する |
| この skill | PRの作成者 → レビュアー | レビュアーが判断する項目と、コードを読む地図をページにまとめて渡す。先に解説せず、レビュアーが書いた理解を受けてから答え合わせする |

## 絶対に守ること

- ページの内容は、PR・diff・CIの実物から書く。実例（コード・画面の状態）は推測で作らず、PRの中から引用する。
- レビュー状態（LGTMのコミット、CIの結果、再確認待ち）は、publishの直前に取り直して正確に書く。
  通っていないものを「通った」と書かない。
- 載せる材料は、PRにある内容（diff・PR本文・CIの結果）と、レビューの結果を自分の言葉でまとめた
  要約、diffから作ったコードリーディングガイド（ファイルの分類・読む順・問い）に限る。レビュアーの出力やログをそのまま貼らない。
- 秘密情報をページに載せない。publishの前に引用部分を見直し、秘密情報らしき値があれば
  載せずに止まり、ユーザーに判断を仰ぐ。
- ページは非公開でpublishされる。共有の設定は変えず、ほかの人に見せる方法（ページの共有メニュー）を
  利用者に伝える。publishしてよいのは、ユーザーの依頼（「PR作成して」による`pr-review-cycle`、
  またはページを作る明示的な依頼）があるときだけ。

## 作るかどうか

**作る**: 機械のレビューでLGTMが出て、人間のレビューへ渡すとき。

**作らない**: 軽微な修正（文言・typo、lintの修正、小さなバグ修正、依存の更新など）。目安として、PR本文の
「確認すること」が2項目以下で、仕様・デザイン・運用の判断を含まない場合は作らない。

迷ったら作る。作らなかった場合は、その理由を完了報告に1行で書く。Artifact toolが使えない、または
publishが拒否された場合も、ページを作らずにその旨を完了報告に書く（PRのマージは妨げない）。

## 手順

### 1. 材料を集める

先に`git fetch origin <ベースブランチ> <PRのブランチ>`で最新にする。

- `gh pr view <番号> --json number,title,body,baseRefName,headRefOid,url` と `git diff origin/<ベースブランチ>...origin/<PRのブランチ>`
- `gh pr checks <番号>`（CIの結果）。CIが実行中なら、`gh pr checks <番号> --watch`をBash toolの
  バックグラウンド実行で走らせ、終わるまで待つ。
  - **CIが失敗していたら、ページを作らない。** `pr-review-cycle`から呼ばれた場合は、同skillの手順6
    （修正）に戻り、手順2・3・4のレビューを経てからこの手順に戻る。単独で頼まれた場合は、失敗を報告して止まる。
- レビューの結果（どのコミットでLGTMか、LGTM後に入ったコミットとその内容）と、PR本文に記録した判断

### 2. ページを書く

Artifact toolの規約に従う。最初に`action: "quickstart"`（intentは`other`）を呼び、その結果にある
ページの規約（ライト・ダーク両方のtheme、スマホ幅、CDNの制限、localStorageの扱い）に従ってHTMLを書く。
見た目と動きは参考ページ（fod-app PR #45: <https://claude.ai/artifact/KUcAvcCSNudXRp9BBZoo3v>、`action: "read"`で
読める）に合わせる。節の構成はこの手順の6節に従い、参考ページは見た目と動きだけに使う。参考ページを
読めない場合は、この手順に書いた6つの節とArtifactの規約だけに従う。

ページの`<title>`は`Portfolio PR #<番号> レビューガイド`に固定する（別のセッションから同じページを探す手がかりにする）。
実例として引用するコード・Mermaidのラベルは、`&`・`<`・`>`をエスケープしてから埋め込む。

ページの上部に、次を出す。

- PR番号・タイトル・コミット、PRへのリンク
- レビュー状態: どのコミットでLGTMか、CIの結果、再確認待ちのもの、人のレビュー待ちであること
- まだ通っていないもの（CI未実行、再確認待ちなど）は、通ったものと見分けられる表示にする
- このページは非公開で、ほかの人に見せるときはページの共有メニューから共有すること

本文は次の6節で構成する。

1. **見るところ・見なくていいところ**
   - 人間が判断すること（見た目・体験・文言・訪問者から見た動き）と、機械（lint・型・test・CI・レビュー）が
     確かめ終えたことを切り分ける。見た目は人間にしか判断できないので、確かめる画面幅・時間帯・
     `prefers-reduced-motion`の条件を書く。
   - 時間の目安を書く。
2. **全体像**
   - Mermaidの図（component構成ならflowchart、状態の切り替えならstateDiagram）と、変更点の一覧表。
   - Artifactは`<pre class="mermaid">`をそのまま描画するので、ライブラリは読み込まない。
   - 図はcomponent・hookの単位までにし、関数の中の処理まで細かくしない（節3で答えを先に出さないため）。
3. **コードリーディングガイド**
   - 人間がコードを読みながら自分で理解するための「地図」。答えを先に説明せず、コードを読まなくても全部分かる
     解説にしない。書いてよいのはファイルの単位のつながりまでで、関数の中の処理・分岐、設計の理由は書かない。
     節の冒頭に「地図を見る → コードを読む → 自分の理解を書く → チャットで答え合わせを依頼する」の流れを書く。
   - 次の6つの小見出しで構成する。
     1. **変更ファイルの分類**: diffの全ファイルを役割（ページ・layout、DOMのcomponent、Canvas / Three.jsのcomponent、
        hook・状態、style、素材、設定、文書など）で分け、各ファイルに役割を1行だけ書く。lockfile・素材は1行にまとめる。
     2. **優先して読むファイル**: 3〜5個を読む順に並べ、それぞれ「なぜここから読むと理解しやすいか」と
        「次に進むファイル」を1〜2行で書く。
     3. **大まかなデータフロー**: 主要な流れを、層を1行ずつ縦に並べて`↓`でつないだASCII図で示す（例: ページ →
        component → hook・state → DOM / Canvasの描画）。データフローがない変更では、その旨と、代わりに処理の入口から
        出口までのファイルの並びを書く。
     4. **自分で読むための問い**: 主要なファイルごとに、答えではなく問い（何のために存在する？どこから
        呼ばれる？いつ描画・再描画される？server / clientのどちらで動く？なぜこの責務をここに置く？訪問者の
        体験のどこにつながる？）を2〜5個ずつ。紙に答えを書き出せる形にする。
     5. **必要なら深掘りするポイント**: `prefers-reduced-motion`、描画ループと止める条件、GPU資源の破棄、
        画像の読み込み、server / client componentの境界など、変更に関係するものを「ポイント → 見る場所」の表にする。
        説明は書かない。
     6. **自分の理解**: 「このPRは何をしている？」「データフロー」「気になった設計」「訪問者の体験とのつながり」
        「分からなかったこと」の5つの入力欄。入力はlocalStorageに保存し（読み書きはtry/catchで囲む。key例:
        `portfolio-pr<番号>-reading-v1`）、「答え合わせ用にコピー」ボタンで、答え合わせの依頼文と`### 自分の理解`以下の
        Markdownをまとめてコピーできるようにする。依頼文には、PRのURLとページに書いたLGTMのコミット（40文字のSHA）を
        入れる。入力内容を画面に表示し直すときは`textContent`を使う。
   - 「確認すること」の進み具合のバーには数えない。
4. **確認すること**
   - PR本文の「確認すること」を、項目ごとに開閉できるチェックリストにする。各項目にPRへのリンクを付ける。
   - 各項目に「説明」「実例（PRの中の実物からの引用）」「OKの基準」を書く。
   - チェック状態はlocalStorageに保存する（key例: `portfolio-pr<番号>-review-v1`）。読み書きはtry/catchで囲み、保存できなくても
     表示は崩さない。
   - チェック状態は項目ごとの識別子（例: `data-key="reduced-motion@1"`）に結び付け、識別子に版を含める。
     項目の説明・実例・OKの基準を変えたら版を上げ、その項目だけ未確認に戻す。
   - 上部に進み具合のバーを出す。すべてにチェックが付いたら、チャットに貼れる返事をコピーボタン付きで出す。
5. **このPRで決めたこと**: 人間が判断したことを、理由を1行ずつ添えて並べる。
6. **ファイルの場所**: 見たいもの → pathの表。

### 3. publishする

- このセッションでまだURLを持っていなければ、publishの前にArtifact toolの`action: "list"`で
  手順2で決めたタイトルのページを探す。あれば`action: "read"`で読み、その`url`を指定して更新する
  （同じPRのページを重複させず、閲覧者のチェック状態を引き継ぐため）。
- HTMLはscratchpad（なければOSの一時ディレクトリ）に置き、リポジトリには置かない。
- 初回は`icon`と1文の`description`を付けてpublishする。
- 同じPRに後から修正が入ったら、**同じファイルを編集して再publishする**（URLが変わらず、閲覧者の
  チェック状態も残る）。上部のレビュー状態を更新し、内容が変わった確認項目は版を上げて未確認に戻す。

### 4. 渡す

ページのURLを、何を確かめるページか（項目数と時間の目安）と、非公開であることを添えて渡す。
コードリーディングガイドの「自分の理解」を埋めて貼ってもらえれば答え合わせをすることも、1行で添える。

### 5. 答え合わせ

人間が「自分の理解」を貼って答え合わせを頼んだら、そこで初めて、コードを根拠に答え合わせをする。根拠にするのは、
依頼文に書かれたLGTMのコミットのコードとする。

1. URLのowner/repoが`gh repo view --json nameWithOwner`と一致し、PR番号が整数、コミットが16進の40文字のSHAで
   あることを確かめる。合わなければ取得せず、人間に確かめる。
2. `gh pr view <番号> --json headRefOid`でPRの今の先端を確かめ、`git fetch origin pull/<番号>/head`で取る。
   LGTMのコミットが手元になければ`git fetch origin <LGTMのコミット>`で取る。それでもなければ、その旨を伝えてから
   PRの先端を根拠にする（黙って先端にすり替えない）。
3. LGTMのコミットと先端が違えば、`git diff <LGTMのコミット> <headRefOid>`で差を確かめ、説明に関わる場合は触れる。

そのうえで、次を説明する。

- 間違っている理解（どこが違い、実際はどうなっているか。ファイル・行を示す）
- 抜けている重要ポイント
- 設計上重要な点（なぜこの責務・形にしたか）

合っている部分は短く認め、人間の書いた理解を書き直して渡すことはしない。「分からなかったこと」には
個別に答える。答え合わせの中でコードの誤りが分かった場合は、説明で終えず、人間に直すかを確かめ、直すなら
人間のレビューの指摘として扱い、直したらガイドを更新する。
