# AIコードレビュー指針

このポートフォリオサイト（Next.js App Router / React）のコードレビューにおける運用ルールと観点を定義する。
サイトの世界観とデザインの判断基準の正本は`CLAUDE.md`であり、この文書には複製しない。レビュー品質を
継続的に改善するため、このディレクトリは生きたドキュメントとして扱う。

## 1. 運用

- レビューは原則として全差分を対象にする。差分だけで判断できない場合は、関連する
  コンポーネント、hook、型、設定、画像も確認する。
- レビュー開始時に必ず [`security.md`](./security.md) を読む。セキュリティは最重要
  観点である。
- UI・体験・デザインの変更では、`CLAUDE.md`の「このサイトの前提」「避けるもの」と照らし合わせる。
- 指摘には重大度、該当ファイル・行、根拠、影響、具体的な修正案を付ける。十分な根拠を
  得られないものは「要確認」とし、事実と推測を区別する。
- Critical、High、Medium の指摘がなければ `LGTM` と明記する。無理に改善案を
  捻出しない。
- ローカルで依頼されたレビューはチャットへ出力する。ユーザーの明示的な依頼なしに、
  プルリクエストへの投稿や承認は行わない。
- 見落としや継続的な誤検知が判明したら、この README または該当観点ファイルを
  更新する。

## 2. 重大度

| 重大度 | 定義 | 対応 |
| --- | --- | --- |
| 🔴 Critical | 秘密情報の漏洩、訪問者の情報の意図しない外部送信、サイトが表示されない | マージ前に必ず対応 |
| 🟠 High | 悪用または重大な不具合（特定の端末・ブラウザで表示が崩れる・固まる、操作できない）につながる可能性が高い | 原則マージ前に対応 |
| 🟡 Medium | 限定的な影響、保守性、アクセシビリティ・性能の不足、`CLAUDE.md`の「避けるもの」に当たる | 対応を推奨 |
| 🔵 Low | 軽微な改善提案 | 任意 |

## 3. 変更種別ごとの確認

| 変更内容 | 最低限確認する観点 |
| --- | --- |
| すべての変更 | `security.md` |
| 動き（CSS animation・transition、`useFrame`、scroll連動） | `prefers-reduced-motion`で止まる・弱まるか。JSで止める動きは、表示した時点の1回だけでなく、閲覧中に設定が変わっても追従するか（`matchMedia`の`change`を購読しているか）。Web Animations（`element.animate()`）で始めた動きはCSSのmedia queryでは止まらないので、動いている途中に設定が変わったときも終わらせているか（`cancel()`は`finished`をrejectし、その後の遷移まで止める。遷移を続けるなら`finish()`）。ページを離れた・unmountしたときに進行中の動きを取り消し、後から遷移などが走らないか。JSで始めたなめらかなスクロール（`scrollBy({ behavior: "smooth" })`等）も同じく、動いている途中に設定が変わったら止める・着地させるか、遷移などで要素の位置を測る前に止めているか（`overflow: hidden`はプログラムからのスクロールを止めない）。最初は隠して視界に入ったら現す要素は、`IntersectionObserver`の`rootMargin`を`%`で書いていないか（画面の幅を基準にすることがあり、横長の大きな画面ではページ末尾の要素が帯に届かず隠れたまま残る）、隠れたままの要素にキーボードのフォーカスが入っても見えるか。常に何かが動いていないか。CSSで止める指定（`@media (prefers-reduced-motion: reduce)`の中）が、hover・フォーカス時の動きの指定（`.a:hover .b`等）より詳細度が低く、負けていないか。動きの量が`CLAUDE.md`の「避けるもの」（大きなカメラ移動、激しいscroll連動、強いBloom等）に当たらないか |
| Three.js / React Three Fiber | geometry・material・textureを作った側が破棄しているか（unmount・再生成でGPUメモリが増え続けないか。R3Fは`<primitive>`で渡した物と`useLoader`のtextureを破棄しない。three の examples の部品は render target を破棄する手段を持たないことがある）。描画ループが不要なときに止まるか（`frameloop`、画面外・タブ非表示）、120Hzなどの画面で描く回数に上限があるか、解像度（DPR）を見た目に効く範囲に抑えているか。color space・tone mappingの設定。WebGLが使えない・context lossのときにDOMの表示だけで成り立つか。three r163以降はWebGL2だけなので、事前の確認はWebGL2で、本番のCanvasと同じ条件（`failIfMajorPerformanceCaveat`など）で行うか。自分で付けた`webglcontextlost`の見張りを、unmountの前（effectのcleanup）に外しているか（R3Fは破棄のときに自分で`forceContextLoss`するので、残すとunmountや`prefers-reduced-motion`での取り外しを失敗と扱い、設定を戻しても戻らない）。静止画と重ねて位置を合わせるcanvasは、縦長・横向きのスマホ・正方形に近い窓など、静止画が高さで合う場合と幅で合う場合の両方で、水平線などの基準が一致するか（`object-position`と箱の縦横比から計算する）。詳しい監査は`developing-threejs-apps` skill |
| 画像・動画・フォントの追加、画像を置く箱の大きさの変更 | 表示サイズに対して大きすぎないか（`next/image`のサイズ指定、形式）。LCPに当たる画像の読み込み優先度。`alt`。不要になった素材が残っていないか。画像を置く箱の大きさを media query で変えたら、その箱に入る画像の`sizes`もすべて同じ条件に合わせたか（TOPでは空・建物・植物・展示室の4か所に分かれている）。`inset`で箱を広げた分や、`object-fit: cover`で高さに合わせて箱より広く描く分（縦長の画面で上へ伸ばした空など）を含めて、宣言した幅が実際に描く幅を下回らないか（宣言した幅でも元画像の幅以上の候補が選ばれる場合は下回ってよい。そう判断した箇所にはコメントで元画像の幅を書き、素材を差し替えたら確かめ直す） |
| レイアウト・タイポグラフィ | スマホ幅（360px前後）で横スクロールや重なりが出ないか。文字の大きさ・行間・コントラスト。画像のレイヤーの上に置いた文字は、その画像が読めなかったとき（失敗・遅延）にも、下の背景色に対して読めるか。画像の位置を画面の縦横比で決めている場合は、正方形に近い窓・縦長の画面でも、主になるもの（入口のアーチ、水平線と建物の関係など）が画面に残るか。幅で分けた media query（`max-width: 767px`と`min-width: 768px`など）の間に、ズームで生じる小数の幅（767.5px）がどちらにも入らない隙間がないか。大きさを決めるルールに見た目の指定（マスク・周辺減光など）が同居している場合、条件を広げたときに見た目の指定まで新しい範囲に掛かり、境目の縦横比で見た目が段差で切り替わらないか |
| 操作できる要素（リンク・ボタン・メニュー） | キーボードで操作でき、フォーカスが見えるか（`outline: none`にするなら、強制カラーモードでも見える代わりがあるか）。`:hover`で内容を出す演出は`@media (hover: hover)`に限っているか（タッチ端末で1回目のタップがhover表示で止まったり、戻ったときにhoverの見た目が残ったりしないか）。hoverで開く表示（メニュー等）は、クリックで開く場合と同じstateで持ち、`aria-expanded`が表示と一致し、マウスが乗ったままでもEscapeで閉じられるか（CSSの`:hover`だけで開くと、Escapeで閉じられない）。キーボードで中を操作している間に、マウスが離れただけで閉じないか。Escapeで閉じたとき、ほかの場所にあるフォーカスを奪わないか。押せない状態のボタンを`disabled`にして、押した直後にフォーカスを見失わないか（`aria-disabled`で代える）。`button`と`a`の使い分け。外部リンクの`rel` |
| ドラッグ・pointerの操作 | 要素の外でボタンを離したときや、pointer captureを失ったときに、ドラッグの状態が残らないか（`event.buttons`の確認、`lostpointercapture`の後始末）。ホイールの量は`deltaMode`で単位が違う（行・ページ単位で送る環境がある）ので、px に換算してから小さな量の判定をしているか。縦のホイールを横の移動に使う場合は、その要素の上にあり、要素がほぼ画面に入っている間だけにし、先頭・末尾ではページの縦スクロールに戻しているか（ページ全体を奪わない。縦にスクロールしている途中から切り替えない）。なめらかに寄せる場合、端の判定を向かう位置ではなく実際の表示位置で行い、寄せている途中にページへ渡して縦と横が同時に動かないか（要素の外で回したホイールや、ズーム・端などでブラウザに任せるときも、寄せている途中の動きを止めているか。ボタンなどで始めたブラウザの smooth scroll も、同じ処理で止まるか）。トラックパッドの横の操作・Shift + ホイール・ピンチのズームはブラウザに任せているか。タッチはブラウザのスクロールに任せているか。同じ操作がキーボードでもできるか。スクロールバーの代わりに位置を示す表示（線の上の光など）を置く場合、展示の幅や間隔がそろわないときや、先頭・末尾に余白があって端の展示を中央に置けないときも、いま見ている展示と表示が一致するか（スクロールした量の割合だけで決めていないか）。表示を scroll イベントだけで更新していると、画面の向きや大きさの切り替えでスクロールの箱が作り直され、位置だけが戻ったときに表示が食い違うので、切り替えのときにも測り直しているか（矢印などの行き先も、覚えた番号ではなくその時点の位置から決めているか） |
| client componentの追加（`"use client"`） | serverで足りるものをclientにしていないか。bundleに重いライブラリ（three等）を読み込む範囲が広がっていないか（`dynamic` importで必要な画面だけに限るか）。`dynamic` importより前に読む共有のファイル（error boundary・事前の確認など）が、`import type`以外でthree等をimportしていないか（1つでも混ざると最初のbundleに入る。`pnpm build`の後、ページのHTMLが読む`<script>`のchunkに含まれていないかで確かめる） |
| 重ねた画像の合成（`components/museum/LayeredBuilding`、`mix-blend-mode`・`mask-image`）と建物の素材の差し替え | 差し替えた素材の外形・開口部が、位置を数値で持つ定義（`components/top/scene.ts`の`opening`等）と合っているか（素材のalphaを測って確かめる。ずれると展示室との間に隙間ができる）。重ねる素材どうしの外形がそろっているか（素地の外にはみ出した画素はmultiplyにならず灰色の縁になり、素地を覆わない画素には陰が乗らない）。光など、マスクで色を足す層も素地の外形で切り抜いているか（光のマスクの白い範囲は、素地の外まで広がっていることがある）。multiplyの層は、影のない部分が白に近いか（灰色だと壁全体が暗くなる）。上に置いた文字（部屋名・壁の案内）のコントラストを、旧素材と比べて、どの時間帯でも、中央値ではなく暗い側の値で確かめたか。CSSのマスク・背景（`background-image`）で読む画像も、舞台を出す前の待ち合わせ（`data-await-images`）に入っているか。`mask-mode`に対応しない環境で、四角い面が出ないか |
| 時間帯による見た目の切り替え（`components/museum/ambient.ts`・`AmbientRoot`） | 基準の夕方（`FALLBACK_AMBIENT`）の値が変わっていないか（足した層は夕方で透明・係数は1か）。サーバーの値から実際の時間帯へ移る最初の切り替えに transition が付いて、舞台のフェードインと重なって色が移り変わる様子が見えないか。filter は時間帯の間で同じ関数を同じ順に並べ、補間できるか。画像の上に置いた文字（館名・Menu・部屋名・壁の案内）が、どの時間帯でも、縦長の画面で空の上に来る場合も含めて読めるか。時刻の判定がサーバーの時刻・固定のタイムゾーンに頼っていないか。確認用の指定（`?ambient=`）が本番で効かないか |
| 計測・外部スクリプト（GTM等） | `security.md` §2 |
| `.env*`、`next.config.ts`、依存、CI、`.claude/`・`scripts/`の変更 | 秘密情報、公開設定、サプライチェーン、権限。人が見ていない間に動く自動化（`scripts/`・`.claude/`のskill）は、失敗・ハング時の後始末と、誰でも決められる値（fork PRのbranch名等）を信頼していないか |

## 4. レビュー出力

各指摘は次の形式を使う。

```text
🔴 [タイトル]
場所: components/path/file.tsx:12
根拠: 仕様または実装上確認できる事実。
影響: 起こり得る訪問者・表示・性能への影響。
修正案: 実装可能な修正方法。
区分: 修正が必要 / 任意改善 / 要確認（前提: ...）
確信度: 高 / 中 / 低（低い場合は確認すべき前提も書く）
```

良い点はレビュー全体の短いサマリにのみ記載し、修正を要する指摘と混在させない。
